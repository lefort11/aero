Основная программа aero
======================

Из корня проекта выполните

  make programs
  ./bin/aero --input=./templates --output=./results

Цель programs собирает Release-версии aero, mesh_converter, meshdec и fields_to_tecplot.
GNU Make использует оптимизацию -O3, определение NDEBUG и отдельный каталог
объектов Release/O3.
make clean удаляет объектные файлы, библиотеки проекта и исполняемые файлы
текущей платформы из каталогов сборки и публикации. В MSYS2 эта цель
также очищает варианты GPU.
Сетки, поля и установленные библиотеки CGNS/HDF5 сохраняются.
Тесты собираются и запускаются отдельной командой make test.
Для сборки одного солвера есть make aero.
По умолчанию GNU Make использует STATIC_LINK=1. В MinGW/x64 библиотеки проекта,
libstdc++, libgcc, OpenMP и winpthreads линкуются статически; для конвертера
используются статические архивы CGNS/HDF5 из build/deps/install, когда они установлены.
Для чистого каталога поставки можно задать BIN, например make programs BIN=build/package.
В Windows CUDA-модуль и CUDA Runtime статически входят в aero.exe. Сборка
по умолчанию включает MS-MPI и использует установленную msmpi.dll.
В Linux STATIC_LINK=0 включает динамическую линковку.

В Linux для сборки нужны GNU Make, GCC/G++ с C++11, статические системные
библиотеки и libgomp для OpenMP. Для конвертера с CGNS нужны также CMake и
sha256sum. Исходные архивы CGNS и HDF5 входят в third_party. Для сборки
достаточно файлов проекта и установленных инструментов.

  make -j4 programs
  OMP_NUM_THREADS=2 make -j4 test
  make -j4 programs KOKKOS_BACKEND=cuda CUDA_HOME=/usr/local/cuda CUDA_ARCH=86

CUDA_ARCH задаёт архитектуру GPU для nvcc, например 86 для sm_86.
При STATIC_LINK=1 Linux-сборка CPU без MPI полностью статическая. В CUDA-сборке
cudart, libgomp и библиотеки C++ линкуются статически. Системные glibc,
libm и загрузчик остаются динамическими для работы драйвера NVIDIA.
Для сборки CPU достаточно первой команды. WITH_OPENMP=0 отключает OpenMP,
WITH_CGNS=0 собирает конвертер с поддержкой Gmsh и another. Linux использует
build/linux для объектов проекта и build/deps/linux для библиотек конвертера.

В Windows используйте терминал MSYS2 MinGW64. Команда make programs KOKKOS_BACKEND=cuda собирает статический солвер для CPU и GPU. Для GPU требуются CUDA Toolkit 12, Clang, LLD и библиотеки CRT Visual Studio. CUDA_HOME задаёт каталог Toolkit, CUDA_ARCH — архитектуру GPU. Проекты msvs/aero.sln вызывают тот же Make. В MSBuild по умолчанию включены CUDA, OpenMP и MPI. Для сборки CPU передайте /p:KokkosBackend=cpu. Подробные команды приведены в README.md в корне проекта.

Для нового запуска с multi = 1 укажите новый каталог результатов.

Подготовка
----------
В начале aero показывает параметры main.txt, gamma из gas.txt, выбранные
устройства CUDA, зоны output.txt, формулы или файл начальных условий и
правила границ. После чтения сетки выводятся её размерность, числа узлов,
элементов и таблица Boundary label / Faces. Число граней берётся из сетки
до объединения периодических границ. Поддерживаются текстовые, бинарные и
сжатые сетки.

При отсутствии bc.txt программа создаёт в каталоге --input секцию для каждой
метки. В пакетном режиме она завершает работу с кодом 2, если нужно заполнить
условия. В интерактивном режиме можно исправить и существующий файл:

  .\bin\aero.exe --input=.\params --output=.\results --interactive

Сохраните bc.txt и нажмите Enter. Программа прочитает файл, проверит покрытие
меток и продолжит расчёт. Для периодической пары оставьте одну секцию с pair
и translation, как в templates/bc.txt. Неверные настройки завершают запуск
с кодом 1. Успешный расчёт возвращает 0.

Расчёт
------
На CPU используются настроенные потоки OpenMP. Для одного процесса CUDA в cuda.txt укажите
номер одного устройства, например devices = 0. Для сборки GPU укажите KOKKOS_BACKEND=cuda. При запуске одного процесса без доступной CUDA программа сообщает
о переходе на CPU. Одна область расчёта обрабатывается одной видеокартой.

Программа строит медианные контрольные объёмы, периодические связи и шаблоны
реконструкции. Для вложенной прямой положительное направление выбирается
по знаку наибольшей компоненты касательной. У плоской сетки аналогично
ориентируется нормаль. Первая ось скорости направлена по проекции мировой X,
а при |n_x| > 0.99 — по проекции Y. На сетке XY используются привычные X, Y.

Невязка собирается по рёбрам из решения текущей стадии. Скорости волн дают
шаг по CFL; он ограничивается ближайшим временем записи и final_time.
Расчёт запускается через calculate_case в solver.cpp. Для .mesh вся сетка
образует одну подобласть. Для .mdec процессы получают свои части из архива.
В сборке без MPI используется тот же решатель с одной подобластью.

Где менять код расчёта

  case_geometry.cpp       prepare_case_geometry читает граничные условия и строит контрольные объёмы.
  partition_state.cpp     PartitionState переводит начальные поля из номеров исходной сетки в расчётные.
  time_loop.cpp           choose_time_step ограничивает шаг, integrate_time принимает его и вызывает вывод.
  solver.cpp              PartitionStepper ведёт стадии Эйлера или SSPRK3 и собирает данные для отчёта.
  partition_operator.cpp  PartitionOperator считает потоки по поверхностям, ограничение CFL и обновление узлов.
  partition_transfers.h   PartitionTransfers упаковывает и обменивает узловые значения и потоки через MPI.
  partition_output.cpp    PartitionOutput записывает поля из одного состояния в локальные или общие файлы.

Например, чтобы изменить момент записи, откройте OutputSchedule в source/io/scheduled_output.cpp.
Чтобы изменить длину шага при известном сроке записи, откройте choose_time_step.

Цикл integrate_time ограничивает шаг по CFL, final_time и расписанию вывода.
PartitionOperator собирает потоки на своих гранях. После выбора шага первая
стадия использует уже собранные потоки. На каждой стадии Эйлера и SSPRK3
ядро update_node суммирует потоки узла и обновляет его состояние. CPU и CUDA
выполняют одну реализацию этой операции. Несколько процессов обмениваются
потоками до обновления и значениями halo после каждой стадии. На одном
процессе обмен пропускается. После принятого шага цикл выводит отчёт,
записывает назначенные поля и recovery. При продолжении расчёта расписание
восстанавливается по сохранённому шагу и времени.

Report работает через report_every. Независимые зоны output.txt
записывают поля по шагам или физическому времени. Каталоги результатов
создаются при подготовке. Файлы полей сохраняют исходную нумерацию сетки,
в том числе при периодике. Синтаксис файлов и полей описан в source/io/README.txt.

Распределённая геометрия CPU
----------------------------
В main.txt можно указать mesh = grid.mdec. Архив meshdec содержит всю
исходную геометрию и граничные метки. Остальные настройки задачи имеют
обычный формат. С одним процессом из архива доступен полный расчёт.

Для подготовки геометрии на нескольких процессах соберите aero с MPI.
В Windows используется Microsoft MPI SDK и runtime, в MSBuild задайте
WithMPI=true. В Linux для сборки с динамической библиотекой MPI выполните

  make -j4 aero WITH_MPI=1 STATIC_LINK=0

Пример для архива, подготовленного заранее на одном процессе

  ./bin/meshdec grid.mesh case/grid.mdec --target-ranks=4
  mpiexec -n 4 ./bin/aero --input=case --output=geometry --geometry-only

Число процессов в mpiexec определяет размещение при этом запуске. Каждый
процесс читает назначенный диапазон листьев из общего файла. При выборе
разрезов вес ветви равен числу байтов несжатых записей плюс 32 байта на
вершину. Лист неделим. Если листьев меньше, чем процессов, лишние процессы
участвуют в обменах с пустой областью.

Разбиение по мощности CPU и памяти узлов
----------------------------------------
Чтобы учесть ресурсы текущего MPI-запуска, добавьте в main.txt параметры.
Пример для четырёх процессов с относительной производительностью 1, 3, 2, 2

  mpi_rank_weights = 1,3,2,2
  mpi_node_memory_mib = auto

Веса задаются в порядке MPI-рангов, начиная с нуля. Одно число задаёт
одинаковый вес всем процессам. Без списка все веса равны единице. Если
задать только mpi_node_memory_mib = auto, учитывается память узлов при
равных весах CPU. Если опустить все параметры mpi_*, действует обычное
разбиение. На одном процессе aero загружает сетку обычным способом.

auto использует доступную физическую память по данным ОС. Чтобы учесть
квоту задания, задайте полный бюджет в МиБ на узел, например
mpi_node_memory_mib = 8192. Для разных узлов можно указать список, например
8192,16384. Узлы перечисляются по возрастанию наименьшего MPI-ранга на них.
Из заданной квоты вычитается суммарная резидентная память уже запущенных
процессов узла. Для сетки берётся меньшее из остатка квоты и доступной RAM.

Процесс 0 выбирает диапазоны цельных листьев сначала для физических узлов,
затем для их процессов. Производительность узла задаётся суммой весов его
процессов. При заданных бюджетах выбираются границы, выравнивающие отношение
работы к мощности узла. Каждый узел получает один непрерывный диапазон,
даже если его MPI-ранги идут вперемешку. Если листьев на узле меньше, чем
процессов, диапазоны получают процессы с большими весами. Точность пропорций
зависит от размера листа. Более мелкие листья можно подготовить через meshdec
с большим --target-ranks.

План строится по дереву и смещениям строк halo до чтения геометрии. Для
диапазона листьев оценка памяти равна mpi_memory_factor, умноженному на
сумму трёх величин

  1. Размер несжатых записей диапазона в байтах.
  2. Размер двух массивов узлового состояния для Эйлера или трёх для SSPRK3.
     На вершину в одном массиве приходится 8 * (dimension + 2) байт.
  3. Число ссылок на ячейки halo, умноженное на среднее число байт архива
     на ячейку (несжатые записи всех сущностей, округление среднего вверх).
     Для версии 2 используются основной и ближний списки, в том числе для
     first_order. Для пятого порядка версия 3 добавляет дальний список.
     В версии 1 доступны только первые две величины.

Коэффициент по умолчанию равен 4 для first_order, 12 для EBR3, 16 для
EBR5 и WENO3, 24 для WENO5. Это начальная оценка временных массивов.
Реальный пик зависит от топологии ячеек, периодических образов и размеров
листьев. Общая halo-ячейка соседних листьев может учитываться несколько раз.
Для калибровки на своей сетке сравните сумму estimated_mesh_MiB по узлу
с приростом памяти от initial_rss_MiB до startup_peaks_sum_KiB / 1024.
Параметр mpi_memory_factor меняет коэффициент пропорционально. Жёсткий
лимит фактической памяти задания задаётся средствами планировщика кластера.

В блоке «MPI CPU placement» выводятся бюджет сетки на узле и полуоткрытый
диапазон [first_leaf, end_leaf) каждого процесса. При нехватке бюджета
решатель сообщает номер первого неразмещённого листа до загрузки подобластей.
Режим --geometry-only использует те же правила размещения. Подходящий архив
можно повторно использовать с другими весами и бюджетами.

В .mdec версий 2 и 3 процесс читает по спискам своих листьев ячейки и их
геометрию непосредственно из архива. Это даёт полную окрестность для
построения MedianDual. Режим --geometry-only записывает геометрию исходной
сетки до отождествления периодических вершин и завершает работу.

В каталоге --output появляется geometry-R-of-P.tsv для каждого процесса R
из P. Внутри файла строки разделены по первому полю. V содержит исходный
номер вершины и объём. E содержит номера концов в порядке возрастания и
три компоненты ориентированной площади. B содержит исходные номера грани,
вершины, метки и три компоненты внешней площади. Внутренние разрезы
исключены из B. Вершину записывает её владелец, ребро — владелец конца с
меньшим номером. Для сравнения запустите тот же режим одним процессом с
исходной .mesh и укажите отдельный каталог --output.

Распределённый расчёт на CPU
----------------------------
В main.txt задайте следующие параметры. Число процессов задаётся при запуске.

  mesh = grid.mdec
  backend = cpu
  reconstruction = ebr5
  time_scheme = ssprk3

  mpiexec -n 4 ./bin/aero --input=case --output=results

Параметр time_scheme принимает euler (явный Эйлер), ssprk3 (три стадии), BDF1
(неявный Эйлер), BDF2 и steady. В режиме steady псевдошаг BDF1 повторяется
до выполнения выбранного в implicit.txt критерия по пространственной невязке.
Первый шаг BDF2 выполняется по BDF1. Следующие шаги
учитывают отношение соседних шагов по времени. Контрольная точка BDF2 сохраняет
предыдущий слой и длину последнего шага. Обе неявные схемы работают на CPU и GPU, в том числе с MPI на сетке .mdec. Число CFL
определяет запрошенный шаг, который может сокращаться до ближайшего срока вывода.
Допуски и решатель задаются в implicit.txt. В отчётный шаг после строки с dt
печатается достигнутая относительная невязка Ньютона по всем компонентам решения.
Параметр reconstruction принимает first_order, ebr3, ebr5, weno3, weno5 и mp5.
Для MPI с EBR3 и WENO3 подходит .mdec начиная с версии 2. Для EBR5 и WENO5
нужна версия 3 или новее с дальним слоем halo. При запуске процесс читает из архива
ячейки выбранного слоя и один раз определяет, какие узловые значения ему
нужны от соседей. Для EBR и WENO одного порядка процесс находит одни и те же
опорные грани. EBR хранит готовую линейную комбинацию, WENO дополнительно
хранит коэффициенты направленных разностей. На каждой стадии Эйлера
или SSPRK3 процессы обновляют значения halo, а WENO вычисляет нелинейные
веса по текущему состоянию. Геометрия нужна только при подготовке шаблона.
Для двумерной характеристической WENO с потоком Роу солвер может упаковать
полные шаблоны для совместного чтения с обеих сторон ребра. На GPU подобласть
до 8192 рёбер включительно использует обычные строки. Тогда все площадки
обрабатываются одним запуском CUDA за стадию. Формула весов в обоих случаях общая.
В init.txt доступны initial_type = formula и initial_type = file. Расчёт поддерживает физические
и поступательные периодические границы, потоки roe и lf, а также настройки
reconstruction_variables из обычного CPU-расчёта. omp_threads задаёт число
потоков OpenMP внутри каждого MPI-процесса.

Перед первым шагом процесс 0 печатает «MPI partition report». В таблице
одна строка на MPI-процесс, включая процессы с пустой подобластью.

  rank, node     ранг процесса и наименьший ранг на узле с общей памятью
  leaves         число назначенных листьев .mdec
  owned, halo    собственные и получаемые от соседей расчётные вершины
  edges          число рёбер, для которых процесс вычисляет поток
  state_send_B, state_recv_B   байты отправленных и полученных состояний
  flux_send_B, flux_recv_B     байты потоков вместе с волновыми скоростями

Периодические копии учитываются как одна расчётная вершина. В halo входят
также удалённые вершины, нужные только для реконструкции. Счётчики обмена
берутся из размеров рабочих буферов на одну стадию. Они включают пересылки
между процессами одного узла. За полный шаг Эйлера проходит одна стадия,
за шаг SSPRK3 — три. Стартовый обмен, служебные заголовки MPI и коллективные
операции в эти байты не входят.

Память указана в КиБ (1024 байта). stencil_peak_KiB — пик резидентной
памяти процесса с запуска по окончание подготовки геометрии и шаблонов.
startup_peak_KiB — пик с запуска до первого шага, включая начальные поля
и буферы обмена. ready_rss_KiB — резидентная память перед первым шагом.
В Windows используются счётчики рабочего набора, в Linux — VmHWM и VmRSS.

В таблице «MPI node memory» приведены имя узла, число процессов и суммы
трёх показателей по узлу. Процессы группируются по общей памяти MPI.
В старых реализациях MPI без этой возможности используются имена узлов.
Пики отдельных процессов могут приходиться на
разное время. Общие страницы памяти могут учитываться у нескольких процессов.
ram_total_KiB и ram_available_KiB — полная и доступная физическая память
узла по данным ОС перед началом расчёта. У задания в планировщике может
быть свой лимит памяти. Если показатель недоступен, выводится n/a.

Для периодической пары задайте в bc.txt исходную метку, парную метку
и перенос из первой во вторую в исходных единицах сетки. Например, для
периода длиной 1 вдоль X достаточно одной секции для обеих меток.

  [xmin]
  bc_type periodic
  pair xmax
  translation 1 0 0

Пары строятся при запуске aero по геометрии .mdec. Для той же сетки можно
менять bc.txt и число процессов без повторного запуска meshdec. Процессы
сопоставляют вершины и грани, проверяют их площади и согласованность
начальных значений. У совпавших вершин одно состояние и суммарный объём.
Владельцем служит процесс исходной вершины с наименьшим номером в группе.
Несколько пар могут сходиться на ребре или в углу. На остальных метках
продолжают действовать заданные физические условия. Для EBR и WENO решатель
дочитывает по граничному индексу ячейки противоположной стороны и
переносит их координаты при подготовке шаблона. Для третьего порядка
строится один слой периодических образов, для пятого — два. Узел на пересечении
нескольких пар получает соседей от всех своих периодических копий.

Каждый процесс обновляет свои вершины и передаёт соседям новые состояния.
Поток на межпроцессном ребре вычисляет владелец его начальной расчётной
вершины. Исходные рёбра ориентированы от меньшего номера вершины к большему.
При объединении периодических рёбер сохраняется ориентация первого из них.
Процесс передаёт соседу поток и волновую скорость. В невязки концов
ребра поток входит с противоположными знаками. Шаг времени одинаков у всех
процессов и ограничен минимальным CFL-шагом по сетке, ближайшим сроком
записи и final_time. В SSPRK3 этот шаг выбирается один раз по состоянию в
начале шага. На каждой стадии процессы вычисляют потоки для её состояний,
обновляют свои вершины и передают новые значения соседям. Для комбинации
стадий каждый процесс хранит состояние начала шага только в своих вершинах.
Снимки и report относятся к полностью завершённому шагу. Глобальный
отчёт учитывает каждую вершину один раз у её владельца.

При выводе зоны с layout = local (по умолчанию) каждый процесс R записывает в каталог
results/rank-R-of-P свою сетку grid.mesh, таблицу nodes.tsv и подкаталог
fields с файлами AEROFIELDS. Снимки используют локальную нумерацию и
содержат актуальные значения соседних вершин. Столбцы nodes.tsv содержат
локальный номер, исходный номер и ранг владельца исходной вершины, начиная
с нуля. В снимке каждой исходной вершине периодической группы соответствует
одно и то же значение поля.
Для сборки глобального поля берите из каждой части строки с владельцем R.
Для просмотра одной части передавайте конвертеру её grid.mesh и снимок.

Общий снимок по исходной сетке
------------------------------

Чтобы получить один бинарный файл AEROFIELDS на всю сетку, задайте для
нужной зоны в output.txt

  [seed]
  layout = global
  file = shared/seed.fields
  every_steps = 100
  multi = 0
  format = binary
  variables = rho, ux, uy, p

При --output=results все процессы вместе записывают results/shared/seed.fields.
В примере двумерной задачи файл обновляется каждые 100 принятых шагов.
Для 3D добавьте uz. Можно выбрать every_time и multi = 1 для серии снимков.
После --recover общие снимки идут в подкаталог resumed-<шаг>-<номер>.

Для MPI нужен архив .mdec версии 4 или новее с SHA-256 исходной сетки. В файле
сохраняются время, шаг и поля в исходной нумерации вершин. Владелец каждой
вершины пишет её значение один раз, включая вершины периодических пар.
Процесс 0 создаёт заголовок и описание полей. Каждый процесс передаёт свои
узловые данные через MPI-IO порциями до 256 КиБ. Снимок публикуется после
завершения коллективной записи. Зоны local и global могут иметь разные
расписания в одном расчёте.
Если все зоны глобальные, каталоги rank-R-of-P для вывода не создаются.

Для нового запуска укажите этот снимок в init.txt. В примере ниже каталоги
case и results лежат рядом. Число процессов нового запуска можно выбрать заново.

Начальные поля и перезапуск на CPU
----------------------------------

Для нового расчёта из глобального снимка AEROFIELDS задайте в init.txt
имена узловых полей. Например, для двумерной задачи

  initial_type = file
  path = ../results/shared/seed.fields
  rho = rho
  ux = ux
  uy = uy
  p = p

Путь отсчитывается от каталога --input. Для консервативного поля со всеми
компонентами вместо этих четырёх строк задайте field = U (см. source/initial/README.txt).
Расчёт начинается с шага 0 и времени 0. При запуске на нескольких процессах
нужны снимок всей исходной сетки и .mdec версии 4 или новее. Каждый процесс проверяет
SHA-256 сетки и хранит поля для своей части. В бинарном файле он переходит
к выбранным узлам по смещениям. Текст и LZMA читаются последовательно.

Для записи состояния расчёта задайте в main.txt интервал в завершённых шагах

  recovery_every_steps = 100

При завершении и по STOP решатель записывает все зоны и контрольную точку.
Нулевой интервал или отсутствие параметра отключает промежуточные точки. Пример первого запуска и продолжения с другим числом процессов

  mpiexec -n 4 ./bin/aero --input=case --output=results
  mpiexec -n 2 ./bin/aero --input=case --output=results --recover

Все процессы должны видеть одну и ту же папку results с правом записи.
Для продолжения за прежним концом расчёта увеличьте final_time в main.txt.
Если веса mpi_rank_weights заданы списком, обновите его для нового числа
процессов. Новое разбиение читает данные по исходным номерам вершин,
восстанавливает время, номер шага, консервативное состояние и опорное поле
для граничных условий. Файл init.txt и снимок начальных полей при этом не требуются.
Для двоичных архивов версий 1–3 используйте при продолжении тот же файл
.mdec. Начиная с версии 4 допускается новая декомпозиция той же исходной сетки,
а на одном процессе также её исходная .mesh. Решатель проверяет сетку,
gamma и соответствие периодических вершин.

В папке --output чередуются два общих файла, recovery-0.bin и recovery-1.bin.
При записи одного другой остаётся доступен. Процесс 0 помечает файл
завершённым после того, как все процессы записали и сбросили данные на диск.

На нескольких процессах чтение и запись узловых данных выполняются
коллективно через MPI-IO. Каждый процесс объединяет свои соседние исходные
номера в диапазоны и передаёт за один вызов до 256 КиБ записей. Процессы
с пустыми частями участвуют в тех же вызовах с нулевым объёмом. Процесс 0
проверяет заголовок. Значения узлов поступают сразу их текущим владельцам.
Формат AERORCV1 общий для однопроцессного и MPI-расчёта. Файлы предыдущих
запусков читаются теми же командами.

При --recover решатель выбирает завершённый файл с наибольшим номером шага.
Если файл оборван или контрольная сумма записи неверна хотя бы на одном
процессе, все процессы переходят к другой копии. Если обе копии непригодны,
расчёт останавливается с ошибкой. До окончания первой записи восстановление
возможно только из ранее сохранённого состояния.

Для продолжения из конкретного файла укажите его номер. Например,
эта команда читает recovery-0.bin, даже если recovery-1.bin новее.

  mpiexec -n 2 ./bin/aero --input=case --output=results --recover 0

Для recovery-1.bin укажите --recover 1. Допустима также запись --recover=0
и --recover=1. Если выбранный файл отсутствует или повреждён, решатель
завершается с ошибкой. Первая запись после продолжения идёт в другой файл.

После перезапуска обычные выходные поля идут в новый подкаталог
resumed-<шаг>-<номер> внутри --output. Это сохраняет поля прежнего запуска,
включая шаги, которые придётся пересчитать после отката. Файлы recovery
продолжают чередоваться в корне --output.

Распределённый расчёт на нескольких GPU
--------------------------------------

Один MPI-процесс ведёт свою подобласть на одной физической GPU. Для двух
карт одного узла укажите в main.txt

  mesh = grid.mdec
  backend = cuda

В cuda.txt перечислите видимые номера устройств в порядке локальных рангов

  devices = 0,1

Для Linux сборка и запуск из корня проекта выглядят так

  make -j4 aero meshdec WITH_MPI=1 KOKKOS_BACKEND=cuda STATIC_LINK=0 CUDA_ARCH=86
  ./bin/meshdec case/grid.mesh case/grid.mdec --target-ranks=2
  mpiexec -n 2 ./bin/aero --input=case --output=out-gpu

Выберите CUDA_ARCH для установленных карт. В Visual Studio включите
WithMPI=true и KokkosBackend=cuda. Для проверки двух видимых устройств
на одном узле выполните make mpi-gpu-test WITH_MPI=1 KOKKOS_BACKEND=cuda.

На каждом узле отсчёт локальных рангов начинается заново. Например,
при двух процессах на каждом из двух узлов список 0,1 применяется на
обоих узлах. Если планировщик выделил каждому процессу отдельную карту
через CUDA_VISIBLE_DEVICES и процесс видит ровно одну GPU, задайте
devices = 0. Перед загрузкой сетки процесс 0 печатает ранг, локальный
ранг, номер устройства и его PCI-адрес. При нехватке видимых устройств
или назначении одной физической карты двум процессам на узле запуск
завершается с диагностикой.

Архив .mdec, настройки реконструкции, периодики и схемы по времени
те же, что у MPI на CPU. На GPU постоянно хранятся локальные состояния,
геометрия и шаблоны. Владелец вычисляет поток на грани один раз. На каждой
стадии упакованные потоки и значения halo передаются через закреплённую
оперативную память узла. Буферы отправки и приёма выделяются при подготовке
подобласти и используются на всех стадиях. Копирования CUDA ставятся в очередь
для всех соседей; MPI получает доступ к буферам после завершения копирований
с карты. После приёма копирование на карту и распаковка идут в одном потоке
CUDA со следующими вычислениями. Для сообщений до 128 байт включительно
ядро упаковки или распаковки обращается прямо к закреплённому буферу, если
CUDA предоставила для него адрес на устройстве. Для остальных сообщений
используется асинхронное копирование. Для CFL каждая GPU вычисляет минимум по своим
вершинам, затем MPI выбирает общий шаг. Отчёт по течению получает значения
собственных вершин. Для записи полей и recovery копируется состояние
локальной подобласти. Форматы файлов позволяют продолжить расчёт на другом
числе GPU или на CPU.

По умолчанию MPI измеряет производительность выбранных GPU перед разбиением
.mdec. Можно также явно указать в main.txt

  mpi_rank_weights = auto

Каждая карта вычисляет потоки выбранным решателем на одинаковом наборе
трёхмерных граней с узловыми состояниями. После прогрева берётся медиана
пяти серий. В строке «MPI GPU calibration» указаны число граней в секунду,
вес относительно самой быстрой карты и размер пробы. Это оценка скорости
вычисления потоков. На время полного шага влияют также реконструкция и обмен
halo. Калибровка учитывает наименьший бюджет памяти среди карт и освобождает
временные массивы до чтения подобластей. Если места нет даже для минимальной
пробы, решатель сообщает об этом и использует равные веса.

Разбиение распределяет оценочную работу пропорционально весам, округляя
границы до целых листьев и соблюдая бюджеты памяти. При повторной попытке
размещения используются уже измеренные веса. Значения mpi_rank_weights,
заданные числом или списком по глобальным рангам, отключают калибровку.
Бюджет mpi_node_memory_mib относится к общей
оперативной памяти процессов узла.

При расчёте на нескольких GPU решатель автоматически запрашивает у CUDA
свободную память каждой выбранной карты. Для подобласти он использует до
95 процентов свободной памяти, оставляя запас драйверу. Веса процессов
задают желаемую долю работы, а бюджеты ограничивают размер подобластей.
Перед запуском можно дополнительно уменьшить лимит в main.txt, например

  mpi_gpu_memory_mib = 8192,4096

Единицы — МиБ. Первое число относится к глобальному рангу 0, второе —
к рангу 1, независимо от порядка карт в cuda.txt. Одно значение задаёт
общий предел для каждой карты. При пропуске параметра или значении auto
используется только автоматически измеренный бюджет.

Первый план строится по дереву .mdec. После подготовки геометрии и таблиц
обмена решатель повторно запрашивает свободную память и считает размер
всех массивов по фактическому разбиению. В него входят состояния основных
и halo-вершин, в том числе дальние значения для реконструкции, строки EBR
и WENO, геометрия, потоки, рабочая память стадий и CFL, индексы и буферы
пересылки каждому соседу. Карта резервирует под них один блок с учётом
выравнивания. MPI начинает расчёт после успешного резервирования на всех
картах. После загрузки упакованных шаблонов WENO/MP5 и списка остальных
площадок решатель освобождает их промежуточные копии в памяти хоста.

Строки «MPI GPU budget» показывают свободную память и бюджет каждого ранга.
В «MPI GPU fit» указаны полуоткрытый диапазон листьев, точный размер блока
(required_bytes), бюджет (budget_bytes) и результат резервирования. Если для
ускоряющих буферов не хватает места, процесс повторяет резервирование на тех же
листьях с исходным разреженным шаблоном и вычислением газа и нормалей на ребре.
Если места всё ещё мало, процессы освобождают пробные блоки, меняют границы по измеренным
размерам и заново строят halo и шаблоны. Для этого используется тот же
.mdec. Если подходящее размещение целых листьев найти не удалось, решатель
завершается до записи полей и recovery. Более мелкие листья дают больше
вариантов размещения.

Замеры времени на CPU и GPU
---------------------------

Для одного процесса и для MPI задайте в main.txt

  mpi_timing = 1

По умолчанию замеры выключены. После расчёта процесс 0 печатает таблицу
в секундах. Счётчики начинаются перед циклом по времени, в том числе при
--recover. Время подготовки сетки, заполнения начального halo и чтения
recovery и калибровки GPU в таблицу не входит.

  flux_compute    реконструкция на гранях и вычисление численных потоков
  stage_update    сборка невязки в узлах и обновление состояния на стадии
  halo_exchange   обновление значений состояния в halo после каждой стадии
  flux_exchange   пересылка вычисленных потоков и волновых скоростей
  cfl             вычисление допустимого шага и выбор минимума по процессам
  output_readback копирование состояния GPU в память узла для вывода и recovery
  fields_write    запись всех зон полей, назначенных на этот шаг
  recovery_write  запись очередной контрольной точки
  integration     весь цикл по времени, включая обновление состояния и вывод

Для подробного разбора неявного шага включите mpi_timing = 1 и задайте
переменную окружения AERO_PROFILE_BDF=1 при запуске. В отчёте отдельно
появятся время сборки конвективной и вязкой частей матрицы, подготовка
предобуславливателя, решение BiCGSTAB и начальное приближение с помощью
предобуславливателя. На GPU такой замер ждёт окончания каждой из этих
операций. Для сравнения общей скорости используйте обычный запуск.

Таблица показывает прошедшее время на стороне процесса. На GPU отсчёт
вычислительной фазы включает запуск и ожидание результата. Обе строки
обмена включают упаковку, пересылку MPI и распаковку, на GPU также копирование
между картой и памятью узла. При включённых замерах процесс дожидается
завершения распаковки перед остановкой таймера соответствующего обмена.
При запуске на одном процессе обе равны нулю. В SSPRK3 потоки и обмены
на нескольких процессах выполняются три раза за шаг, выбор CFL — один раз.
В fields_write один вызов соответствует одному шагу вывода при любом числе
зон. Если поля и recovery записываются на одном шаге, output_readback
учитывает одну общую копию. На CPU этот счётчик равен нулю.

calls_per_rank показывает число вызовов на каждом процессе. min_s, mean_s
и max_s относятся к накопленному за запуск времени одной фазы по процессам.
max_s_per_step равен max_s, делённому на число принятых шагов текущего
запуска. При продолжении после recovery это разность end_step и start_step.
При нуле шагов в этом столбце стоит n/a. Перед началом замеров процессы
синхронизируются один раз. Статистика собирается после цикла.

Для проверки сильного масштабирования запускайте один и тот же архив
на разном числе процессов при одинаковых схеме, интервале расчёта,
расписании вывода и числе потоков OpenMP на процесс. Например,

  mpiexec -n 1 ./bin/aero --input=case --output=out-1 > cpu-1.log
  mpiexec -n 4 ./bin/aero --input=case --output=out-4 > cpu-4.log

На кластере задайте размещение процессов средствами планировщика.
Для ускорения разделите max_s строки integration базового запуска на
max_s этой строки у сравниваемого запуска. Если сетка помещается только
на нескольких узлах, за базу можно взять минимальную рабочую конфигурацию.
Сравнивайте фазы по отдельности. Их максимумы могут приходиться на разные
процессы и в сумме не дают время интегрирования.

Для сравнения одной и двух GPU укажите в --devices сначала быструю карту
и выберите новый каталог --work. Пример для Windows

  python qa/mpi_gpu_scaling.py --aero bin/aero.exe --meshdec bin/meshdec.exe --devices=0,1 --work build/gpu-scaling

Скрипт запускает один архив в трёх режимах: быстрая карта, две карты
с равными весами и две карты с автоматическими весами. Порядок меняется
между тремя повторами. В runs.csv сохраняются максимумы фаз по рангам,
полное время запуска job_s и расхождение итоговых полей.

Проверки
--------
  make aero-test
  make mpi-geometry-test WITH_MPI=1
  make mpi-balance-test WITH_MPI=1
  make mpi-timing-test WITH_MPI=1
  make mpi-recovery-test WITH_MPI=1
  make mpi-fields-test WITH_MPI=1
  make mpi-euler-test WITH_MPI=1
  make mpi-ssprk3-test WITH_MPI=1
  make mpi-periodic-test WITH_MPI=1
  make mpi-ebr3-test WITH_MPI=1
  make mpi-ebr5-test WITH_MPI=1
  make mpi-weno3-test WITH_MPI=1
  make mpi-weno5-test WITH_MPI=1
  make test

Сквозные тесты запускают aero отдельным процессом, редактируют bc.txt во время
паузы, проверяют Эйлера и SSPRK3 и читают полученные файлы AEROFIELDS.
Проект aero_tests запускает те же проверки в Visual Studio. В сборке CUDA
свойство AeroTestDevice выбирает номер видеокарты для теста.

В partition_execution.h общая операция обновляет узлы владельца и отмечает ошибку
в состоянии газа. Типизированный перенос записей использует номера экспорта и импорта
данного раздела. PartitionTransfers управляет буферами MPI и их временем жизни.
При проверке допустимости пробного поля Ньютона на цельной сетке исполнитель сохраняет
узловой газ в штатном буфере. Только непосредственно следующая сборка того же поля
использует результат проверки. После отказа новая попытка проходит свою проверку.
